## T2 探针"永远未授权"的真正根因 + 修复（01:4x 发现，比 Shizuku 启动更底层）
- Shizuku 服务端其实能起来（USB adb 跑 `sh /sdcard/Android/data/moe.shizuku.privileged.api/start.sh` 即可绕过无线调试搜索卡死，pid=shizuku_server 确认在跑）。但 App 的 T2 探针一直拿不到授权。

- **修复**：
  1. Manifest 加 `moe.shizuku.manager.permission.API_V23`。
  2. `ShizukuProbe.requestPermission(activity: Activity?)` 改双参反射（有 Activity 走 `requestPermission(Activity,int)`；无 Activity 走单参兜底，找不到也不置 guard，避免卡死）。
  3. `GuardService.requestShizukuPermission(activity)` 透传。
  4. `MainActivity.btnStart` 点"启动隐私监测"后，延迟 600ms 用 `this@MainActivity`（Activity）发起 `requestShizukuPermission(this)`，弹框让用户点"允许"→ `RequestPermissionResultListener` 触发 `maybeStart` → 打 `ShizukuProbe started (T2 enhanced)`。

- **暴露的新 bug**:`ShizukuProbe` 用 `scheduler.scheduleAtFixedRate(::refresh, 0, 60, SECONDS)`(60s 一轮)。第一轮 dump 成功、出 verdict 后,**调度器再不触发第 2 轮**。根因 = `scheduleAtFixedRate` 的经典陷阱:**任务体一旦抛未捕获异常,会取消后续所有周期执行**。`refresh()` 里 `callback(clients)`(或 parse)若抛异常,就把整个循环静默杀了。App 与 `:shizuku` 进程都还活着,只是不再 tick。

- **复盘/提醒**:
  - `ScheduledExecutorService.scheduleAtFixedRate` 的回调**必须**自己兜底异常,否则一次崩全停。这是比"单点异常"更隐蔽的坑,下次写周期任务直接默认包裹。

## 🔴 Shizuku 探针 bootstrap 缺陷（根因定位 + 修复，约 06:53 本 turn）

- **修复（已落盘 `app/.../probe/ShizukuProbe.kt`）**：
  1. `start()` 里 `maybeStart()` 之后，若 `!running` 则 `scheduler.scheduleAtFixedRate({ maybeStart() }, 5, 5, SECONDS)` 周期性重试，权限一就绪即启动。
  2. `maybeStart()` 成功时 `bootstrapTask?.cancel(false)` 取消重试；`stop()` 也取消。

## 🔴🔴 Shizuku 探针真正根因：Manifest 缺 `<queries>`（约 07:0x 本 turn，最新）
- **真机实测（06:56 干净复现）**：`ShizukuProbe wait: binder not alive` 全程刷屏，但 `ps -A` 显示 **`shizuku_server` pid 20345 uid 2000(shell) 在跑**、`moe.shizuku.privileged.api` pid 29329 在跑、`adb_wifi_enabled=1`、`service.adb.tcp.port` 空、设备 **Android 13 / API 33**。
- **真正根因**：`app/src/main/AndroidManifest.xml` **没有 `<queries>` 声明**。Android 11+(API 30+) 的**包可见性(package visibility)** 限制会让本 App 在运行时"看不见" `moe.shizuku.privileged.api` 的 `ShizukuProvider` → `Shizuku.getBinder()` 返回 null → `Shizuku.pingBinder()` 永远 `false` → 授权框弹不出（`requestPermission` 里的 `if (!isBinderAlive) return` 守卫 + 此坑 = 死锁）→ 探针永久休眠。这是 Shizuku 官方文档明确要求、但本项目漏掉的配置。**这解释了"Shizuku 服务端明明在跑、本 App 却 binder not alive"的全部现象。**
- **已验证 `pingBinder` 方法确实存在**：从 gradle 缓存 `api-13.1.5.aar` 解压 `classes.jar`，`javap` 确认 `rikka.shizuku.Shizuku` 有 `public static boolean pingBinder()`、`requestPermission(int)`（**仅单参，无双参 Activity 版**）、`checkSelfPermission()`、`getBinder()`。所以反射没失败，false 是真实的"服务端不交付 binder"。
- **修复（已落盘）**：
  1. `AndroidManifest.xml` 加 `<queries><package android:name="moe.shizuku.privileged.api"/></queries>`（`<application>` 之前）。低版本忽略该元素，无副作用。
  2. `ShizukuProbe.maybeStart()`：当 `alive && !perm` 时主动 `requestPermission(null)` 拉起授权框（单参版由 Shizuku 以 NEW_TASK 弹出，不依赖 Activity 上下文），打通"服务端可达→自动弹授权→用户允许→探针启动"链路，打破死锁。
  3. `permResultListener`：授权被拒/未决定时 `permissionRequested=false` 复位，允许后续重试（避免一次性锁死）。
- **待用户重建**：`tools\build_apk.bat` → agent `adb install -r` 装机 → 验证预期：约 5s 内 logcat 出现 `ShizukuProbe started (T2 enhanced)`，时间线默认显示系统调用（证明 App 有效），关 `swSystem` 仅第三方。若仍 `binder not alive` 则需排查 Shizuku 服务端是否真以 ADB 模式授权本 App（配对≠授权）。
