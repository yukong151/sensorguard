# SensorGuard 全量代码审查 · Shizuku T2 链路专项

> 审查范围：`app/src`(Kotlin 探针/服务/UI) + `core-rust/src`(规则引擎/FFI/事件窗) + `schemas/sensorguard.fbs` + 两份开发文档
> 真机前提：Moto XT2153 (Android 13)，Shizuku App 已安装
> 结论一句话：**T2 解析器健壮，但归因结果未进入判定引擎，精确采样率被结构性丢弃——T2 当前是"活着的死分支"。**

---

## 1. T2 链路当前架构（as-is 数据流）

```
ShizukuProbe(反射调 Shizuku.newProcess)
   └─ execDumpsys("dumpsys sensorservice")
        └─ SensorServiceParser.parse()  → List<SensorClient{uid,pkg,op,samplingPeriodUs}>
             └─ callback(clients)  [GuardService.onCreate 注入]
                  └─ for c in clients: addSharedActivePair(c.uid, c.op, pkgHashFromName(c.pkg))
                       └─ sharedPairs["uid:op"] = ActivePairData(uid,op,pkgHash)   ← samplingPeriodUs 在此被丢弃
                            └─ batchTick() 每 60s → FbSerde.encodeTickInput(tier, pairs)
                                 └─ sg_tick() → for pair in active_pairs: windows.get_or_create(key)
                                      └─ if pw.changed()  ← 仅当该 (uid,op) 收到过 OpEvent(START/STOP) 才为真
                                           └─ build_eval_ctx(...) → sample_rate_hz = pw.sample_rate_hz()  ← 由事件间隔反推
                                                └─ eval_l2_rules() / verdict::evaluate()
```

**两个结构性断点（致命）：**
- **断点 A**：Shizuku 只调 `addSharedActivePair`，**从不 push `OpEvent`/`sg_push_op`**。而 Rust `sg_tick` 只对 `pw.changed()` 为真的窗口做判定（`ffi/mod.rs:445`），`changed` 只在 `record_ctx`(收到 OpEvent) 时置位（`event_window.rs:167`）。全项目仅有 `MicProbe`/`CameraProbe` 推送 OpEvent，**没有任何 IMU OpEvent 来源**（无 SensorBaselineProbe 推送他人 IMU）。→ T2 发现的 IMU 对永远 `changed()==false`，**不产生任何判定**。
- **断点 B**：`TickInput.active_pairs → ActivePair{uid,op,pkg_hash}` 三字段（`sensorguard.fbs:42`），**无采样率字段**；且引擎 `sample_rate_hz = pw.sample_rate_hz()`（`ffi/mod.rs:200`）是由**事件间隔**反推（1000/avg_interval），并非物理传感器 Hz。Shizuku 提供的权威 `samplingPeriodUs`（如 20000us=50Hz、2000us=500Hz）在 `GuardService:137` 回调处直接丢弃。→ 即便接上断点 A，R108(≥200Hz) 这类依赖精确 rate 的规则仍拿不到真值。

## 2. 审查发现（按严重度）

### P0 — 阻断 T2 实际生效
| # | 位置 | 问题 | 影响 |

- FFI/JNI 手写零依赖、FlatBuffers 字节对齐有 Rust golden 夹具 + Kotlin `FbSerdeTest` 互验，契约可靠。

## 3. 真机实测要点（Shizuku 已装，Moto XT2153）
1. **先验证 Shizuku 授权态**：`adb shell dumpsys sensorservice` 在 Shizuku 授权后能否被 shell 读取；首次需用户在 Shizuku App 点"允许本次/始终允许 SensorGuard"。
2. **抓真实输出**：`adb shell dumpsys sensorservice > /sdcard/sg_dump.txt`，对比 `SensorServiceParserTest.REAL_OUTPUT` 格式，确认 `Active Connection` 行格式（部分机型 handle 前缀/空格/单位可能不同），用真机 dump 扩写解析器单测。
3. **验证 T2 激活**：过滤 logcat `ShizukuProbe started (T2 enhanced)`；若未出现，基本可定位到 P1-1（授权晚于启动）。
4. **验证判定打通**：制造一个 ≥200Hz 的陀螺仪占用（如某健身/手势 App），观察是否产出 `rule=108` 的 ALERT 且 `evidence_tier=T2`、`pkg=真实包名哈希`。
5. **验证退出清理**：停止该 App 后 60s 内 `sharedPairs` 应移除该 (uid,op)，verdict 不再持续。

## 4. 推荐打磨顺序（P0→P1→P2）

**Step 1 · 打通 T2 归因（修 P0-1）**
- `ShizukuProbe` 回调改为 **diff 快照**：对"新增客户端"推送 `ProbeEvent(START, uid, op, pkgHash, ctx=CtxProbe.snapshot())`；对"消失客户端"推送 `STOP` + `removeSharedActivePair`。复用 `pushProbeEvent` 路径（与 Mic/Cam 一致），使 `PairWindow.changed()` 置位。
- 注意：仅 START/STOP（不要每 60s 推 TICK），否则事件数越过 `MIN_EVENTS=20` 会让 L3 用合成事件做无意义 KS 判定。L2 规则（R108 等）不走 MIN_EVENTS 门控，仍会正常触发。

**Step 2 · 贯通精确采样率（修 P0-2）**
- `sensorguard.fbs`：`struct ActivePair` 增加 `sampling_period_us: uint;`；`TickInput` 不变。
- `FbSerde.encodeTickInput` / `ActivePairData` 透传该字段；Rust `sg_tick` 读取后，对 `sampling_period_us>0` 的对，**覆盖** `eval_ctx.sample_rate_hz = 1e6 / period_us`（绕过 `pw.sample_rate_hz()` 的间隔反推）。
- 同步更新 Rust golden 夹具 `make_tick_input` 与 `FbSerdeTest` 字节对齐断言。

**Step 3 · 可靠性（修 P1-1/P1-2/P1-3）**
- 注册 `Shizuku.addRequestPermissionResultListener`（反射）与 `addBinderDeadListener`，授权/失效时 (重新) 启停 `start()`；移除 `permissionRequested` 一次性标志。
- `execDumpsys`：`Process.waitFor(timeout)` + 读 stderr 防挂；超时就 `shutdownNow` 该次任务并 `return`。
- 配合 Step 1 的 diff，停止客户端必须 `removeSharedActivePair`（解决 P1-3 陈旧残留）。

**Step 4 · UI/构建打磨（P2）**
- `DetailActivity.formatVerdict` 增加 `T2` 分支（"等级 T2 增强"）；补齐 `opName` 的 LIGHT/BARO/PROX。
- 决策 `build.gradle.kts:53`：若坚持"可选插件不进主包"，**删除** `implementation("dev.rikka.shizuku:api:13.1.5")`，保留纯反射；若接受进主包，则改用正式 API（含 listener）并删反射代码。二者取一，不要并存。

## 5. 一句话交付建议
先落 **Step 1 + Step 2**（打通归因与 rate 字段，这是 T2 的本体），再用 **Step 3** 保证真机授权时序与健壮性，最后 **Step 4** 收尾 UI/体积。任一 Step 完成后都用 §3 真机清单回归。
